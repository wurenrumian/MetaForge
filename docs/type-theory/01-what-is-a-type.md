# 01 · 类型到底是什么

> **一句话**：类型是一份可以被编译器检查的承诺；把类型读成“命题”、把程序读成“证明”，是进入类型论最省力的一扇门。

## 从一个最小的判断开始

先看一行几乎每个程序员都见过的代码：

```agda
true : Bool
```

在 Agda 里，`:` 读作“具有类型”（has type）。这一行是一个判断（judgment）：

> `true` 这个值，具有类型 `Bool`。

它不像 `1 + 1 = 2` 那样是一个可以被真伪判断的命题，而更像“这张身份证属于这个人”一样的断言。类型论研究的第一件事，就是什么样的判断是合理的，以及我们如何构造出支持这个判断的证据。

日常语言把类型写在变量前面：

```cpp
bool flag = true;
int count = 3;
```

这容易让人以为类型是“变量前面的装饰”。类型描述的是值本身：`true` 之所以能赋给 `bool`，是因为 `true` 这个值属于 `Bool` 这个类型；变量只是给它起了个名字。

## 类型不是“内存布局”

一个常见的误解是：类型就是“这块数据占几个字节、怎么解释”。这在系统编程里很有用，但它只是类型的一个侧面。

看两段都能通过类型检查的 C++ 代码：

```cpp
int divide(int a, int b) {
    return a / b;          // b 为 0 时是未定义行为
}
```

```cpp
std::string_view sv = std::string("hello");
std::cout << sv;           // sv 指向的临时字符串已经销毁
```

第一段的问题是类型没有表达“除数不能为零”；第二段的问题是类型没有表达“这个视图不能活得比原字符串久”。类型系统管的是“形状与操作”，不是“所有语义约束”。

所以更准确的说法是：

> 类型是一份**合同**。它规定“你可以对我做什么”，也规定“我会还给你什么”。合同可以很粗，也可以很细；类型论研究的，就是如何把合同写细，以及如何让机器检查它。

## 三种读法

理解类型有三种常见角度。三者并不互相冲突，是同一件事在不同精度下的投影。

### 读法一：类型是值的集合

最朴素的读法是：一个类型就是一组值。

- `Bool` 是 `{true, false}`；
- `Nat` 是 `{0, 1, 2, ...}`；
- `A → B` 是从 `A` 到 `B` 的所有函数组成的集合。

这个读法很好用。它解释了为什么 `true : Bool` 成立，也解释了为什么 `not : Bool → Bool` 是一个“从布尔到布尔的函数”。

但它很快会碰到边界。比如“长度恰好为 3 的整数列表”当然也是一个集合，可是在普通语言里，你没办法只用一个类型名把它和“长度恰好为 4 的列表”区分开。要让类型表达这种性质，就需要依赖类型（dependent type）：类型可以依赖具体的值。这是第 04 篇的主题。

### 读法二：类型是行为的接口

在工程里，类型更像一份接口说明：

```cpp
template <typename T>
T max(T a, T b);
```

这个签名承诺：只要你给我两个相同类型 `T` 的值，我就还你一个 `T`。它没有承诺 `T` 一定可比较——那是函数体里 `a > b` 的事；也没有承诺 `T` 一定可拷贝——那是调用方式的事。

这就是为什么“类型正确”不等于“程序正确”：类型只覆盖它写出来的那部分合同。

### 读法三：类型是命题

这是类型论最反直觉、也最有威力的一种读法。

把类型 `A` 看成一个命题，把“具有类型 `A` 的程序”看成“对命题 `A` 的证明”。于是：

| 逻辑 | 类型 |
| --- | --- |
| 命题 `A` | 类型 `A` |
| `A` 的证明 | 类型为 `A` 的程序 |
| `A → B`（蕴含） | 函数类型 `A → B` |
| `A ∧ B`（且） | 有序对类型 `A × B` |
| `A ∨ B`（或） | 和类型 `A ⊎ B` |
| 真 `⊤` | 只有一个元素的类型 |
| 假 `⊥` | 没有元素的类型 |

这张表叫 Curry–Howard 对应（Curry–Howard correspondence）。它不是在玩文字游戏：如果你能写出一个类型为 `A → B` 的程序，你就真的构造出了“从 A 推出 B”的证明；如果写不出来，就说明这个蕴含在当前的规则下不成立。

第 05 篇会把这张表逐项展开。现在先看一句话：

> **写程序 = 构造证明；类型检查 = 检查证明。**

## 判断、上下文与规则

类型论喜欢把“在什么前提下，什么东西具有什么类型”写成：

```text
Γ ⊢ t : A
```

读作：在上下文 `Γ` 下，项 `t` 具有类型 `A`。

- `Γ` 是上下文，记录“当前有哪些变量、它们分别是什么类型”；
- `⊢` 是“推导出”的符号；
- `t : A` 是判断。

例如：

```text
x : Nat ⊢ x + 1 : Nat
```

意思是：如果 `x` 是自然数，那么 `x + 1` 也是自然数。这个判断不需要运行程序就能成立。

在 Agda 里，这三样东西都能直接写出来：

```agda
module FirstLook where

data Bool : Set where
  true  : Bool
  false : Bool

not : Bool → Bool
not true  = false
not false = true
```

逐行读：

- `data Bool : Set where` 声明了一个新类型 `Bool`，它“住在” `Set` 里。你可以先把 `Set` 理解成“类型的类型”。
- `true : Bool` 和 `false : Bool` 是 `Bool` 的两个构造子（constructor），也就是 `Bool` 仅有的两个值。
- `not : Bool → Bool` 声明了一个从 `Bool` 到 `Bool` 的函数。
- 最后两行是模式匹配：`not` 收到 `true` 就返回 `false`，收到 `false` 就返回 `true`。

类型已经把“不可能的情况”从代码里删掉了：这里没有“如果输入不是 Bool 怎么办”的分支。输入只能是 `true` 或 `false`，编译器知道这两种情况已经覆盖了全部可能。

## 为什么这很重要

类型检查器在做什么？你可以把它想成一位严格的审核员：

1. 你说 `true : Bool`，它检查 `true` 是不是 `Bool` 的构造子；
2. 你说 `not : Bool → Bool`，它检查函数体在所有输入下都返回 `Bool`；
3. 你说 `not (not b) : Bool`，它把两次函数应用的类型接起来，确认没有断链。

如果审核通过，说明你构造出了一个符合合同的程序。它不会检查：

- 这个合同是不是你想要的；
- 这个函数在业务上是否“正确”；
- 程序会不会死循环（Agda 会额外检查终止性，但大多数语言不会）。

所以类型系统不是“正确性”的万能药，而是“**相对于类型所写规格**的正确性”。规格写弱了，类型就拦不住 bug；规格写错了，类型甚至会帮你把错误固化下来。

## 人话总结

<div class="human-note">
<strong>如果只记住一件事：</strong>类型是合同，编译器是审核员。普通类型只能审核“形状”，依赖类型可以把“数量、范围、顺序”等条件也写进合同。Curry–Howard 则告诉我们：审核一份“证明”和审核一个“程序”，在数学上是同一件事。
</div>

## 常见误解

**误解一：类型就是内存布局。**

不是。`std::vector<int>` 和 `std::array<int, 3>` 的内存布局可能很像，但它们的类型完全不同，因为合同不同：一个可以增长，一个长度固定。

**误解二：强类型语言不会出现运行时错误。**

强类型只排除“类型不匹配”这一类错误。数组越界、空指针解引用、除零、资源泄漏，都可能发生在强类型程序里。Rust 的所有权检查能排除一部分内存错误，但也不能排除逻辑错误。

**误解三：类型检查可以替代测试。**

类型检查证明的是“对所有输入，程序都满足类型合同”；测试验证的是“对某些输入，程序输出符合预期”。两者覆盖的是不同维度。好的工程两者都要。

**误解四：类型论就是研究“怎么给变量标类型”。**

类型论研究的是“类型系统能表达什么、能保证什么、代价是什么”。变量标注只是最表层的一小部分。

## 本章小结

- `t : A` 是一个判断，读作“`t` 具有类型 `A`”。
- 类型可以读成值的集合、行为的接口，或命题；三种读法各有适用范围。
- Curry–Howard 对应把“程序”和“证明”连了起来：类型是命题，程序是证明。
- 普通类型只能表达“形状”，依赖类型可以让类型依赖具体的值。
- 类型检查保证的是“相对于类型规格”的正确性，不是绝对正确性。
