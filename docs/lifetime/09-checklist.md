# 09 · 生命周期检查清单

> **一句话**：生命周期 bug 几乎都不是"没想到"，而是"没问"；这份清单的作用，是把该问的问题变成习惯。

## 怎么用这份清单

前八篇讲的是"为什么"，这一篇只讲"怎么查"。清单的价值在于**顺序**：先问边界，再问数据，最后问并发。顺序反了会很累——你还没搞清楚这个函数拿到的是借用还是拥有，就去检查它有没有加锁，结论一定是虚的。

三个使用场景：

- **写代码时**：写完一个函数，花 30 秒过一遍第 1、3 组。
- **review 时**：按下面的十分钟流程走，不要从缩进和命名开始。
- **改 bug 时**：先定位它属于哪一组，再只看那一组的问题，避免漫无目的地读代码。

清单不是规则。每条问题都可能得到"这里不需要考虑"的答案，但**你必须能说出为什么不需要**。

## 一、存储与作用域

1. 这个对象是栈上的、堆上的、静态的，还是别人给的？它的存储期（storage duration）到哪一行结束？
2. 有没有把局部变量的地址、引用或视图（`string_view`、`span`、`iterator`）带出作用域——通过返回值、输出参数、成员赋值、或者 lambda 捕获？
3. 这个临时对象活到哪？`f(std::string("a"))`、`v.push_back(make())`、范围 for 里的 `auto&&`，各自的临时对象在什么时候销毁？
4. 析构顺序是否被依赖？同一个作用域内的对象按构造的逆序销毁，跨编译单元的静态对象顺序未定义（static initialization order fiasco）。
5. 这个变量是"值变了"还是"对象换了"？移动之后原对象处于有效但未指定的状态，还能不能读？

## 二、所有权与释放

1. 这个资源（内存、文件、句柄、锁、socket）由谁负责释放？答案必须是一个具体的类型或一个具体的人，不能是"大家都会注意"。
2. 用了裸 `new` 吗？如果用了，`delete` 在哪、异常路径上还会执行吗？
3. 拥有权的转移是显式的吗？函数签名能看出来它是"拿走"（`unique_ptr` 按值、`&&`）还是"借用"（`const&`、裸指针、`span`）？
4. 有循环引用吗？两个 `shared_ptr` 互相持有，引用计数永远不会归零。
5. 这个类需要析构函数吗？如果需要，拷贝/移动构造和赋值是否也该定义（Rule of Five / Rule of Zero）？
6. 自定义 deleter 或 `shared_ptr` 别名构造（aliasing constructor）用得对吗？后者不拥有指针指向的对象，只共享控制块。

## 三、引用、指针与视图

1. 这个引用/指针/视图指向的对象，寿命是否严格覆盖它的使用期？
2. 它可能悬垂吗？哪些操作会让它失效——容器扩容、对象析构、`erase`、`realloc`、`reset()`？
3. 它可能为空吗？裸指针和 `weak_ptr::lock()` 的结果都要检查。
4. 这个 `string_view` / `span` 指向的是谁的数据？如果是临时 `std::string`、`substr()` 的结果、或者一个会被修改的容器，它活不过下一行。
5. 引用作为成员变量时，编译器生成的赋值运算符改的是"被引用的那个对象"，不是"让引用改指向别人"——这是你要的语义吗？
6. 有没有把引用存进容器或跨线程传递？这两件事都会让"寿命覆盖"的证明变得困难。

## 四、容器与迭代器

1. 这个循环里会修改容器大小吗？如果会，循环变量是下标、迭代器，还是 range-for 生成的隐式迭代器？
2. `erase` 的返回值接住了吗？`it = c.erase(it)` 而不是 `c.erase(it); ++it`。
3. 有没有在保存迭代器/指针/引用之后，又做了 `push_back`、`insert`、`reserve`、`rehash`？
4. 这个容器是连续存储（`vector`、`string`、`deque` 中间操作）还是节点存储（`list`、`map`、`unordered_*`）？失效规则完全不同。
5. `reserve` 的上界估对了吗？超过容量照样扩容，照样全部失效。
6. 用了 `std::vector<bool>` 吗？它是位压缩特化，`operator[]` 返回代理对象，不能取地址、不能绑定 `bool&`。

## 五、递归与回溯

1. 递归函数里的状态，哪些是每层独立的（局部变量、传值参数），哪些是所有层共享的（引用参数、成员变量、全局变量）？
2. 每一处修改都有配对的恢复吗？恢复语句是否在**下一次循环之前**执行？
3. 恢复的责任边界清楚吗？每一层只撤销自己做的选择，叶子节点不负责撤销父层的选择。
4. 递归深度上界是多少？栈够不够？C++ 不保证尾递归优化，深递归要显式改成迭代。
5. 有没有从递归里返回局部对象的引用/指针，或者把局部变量的地址存进缓存？
6. 记忆化缓存的键覆盖了全部状态吗？缓存放在哪、什么时候清空、多个测试用例之间会不会互相污染？

## 六、并发与异步

1. 每个 `std::thread` 都被 `join`、`detach` 或者交给 `jthread` 了吗？`joinable` 的线程析构会 `std::terminate()`。
2. 线程/回调捕获了什么？捕获 `[&]` 或 `[this]` 时，被捕获对象一定活得比线程久吗？
3. 共享数据有同步吗？`std::mutex`、`std::atomic`、还是根本不该共享？
4. 对象的销毁会不会和回调的执行撞上？用 `weak_ptr::lock()` 兜底了吗？
5. `std::async` 返回的 future 被保存了吗？丢弃它等于同步等待 + 吞掉异常。
6. 取消是协作式的吗？`stop_token`、`context`、`CancelledError` 都需要被检查，没人能强行杀死一个线程。

## 红色信号表

看到这些代码味道，先停下来问一句。

| 代码味道 | 可能的问题 | 追问 |
| --- | --- | --- |
| `return local_ref;` / 返回 `const T&` 绑局部 | 悬垂引用（UB） | 被引用的对象在调用方那里还活着吗？ |
| `std::string_view` 作为成员变量 | 指向的字符串可能已销毁 | 构造它的那个 `string` 归谁所有？ |
| `t.detach()` + `[&]` | 悬垂 + 数据竞争（双重 UB） | 线程结束时，捕获的对象还在吗？ |
| `[this]` 出现在异步回调里 | use-after-free | 对象析构时，回调会被取消吗？ |
| `c.erase(it)` 之后继续用 `it` | 迭代器失效（UB） | 接住返回值了吗？ |
| `for (auto& x : v) v.push_back(...)` | 迭代器失效 + 可能死循环 | 循环里为什么要改大小？ |
| `shared_ptr` 互相持有 | 内存泄漏（不是 UB，但同样致命） | 其中一边能改成 `weak_ptr` 吗？ |
| 持有 `std::mutex&` 的 `lock_guard` 活过了 mutex | 悬垂锁对象（UB） | 锁对象的生命周期覆盖临界区吗？ |
| `std::async` 的返回值被丢弃 | 隐式串行 + 异常丢失 | 是要后台执行，还是要结果？ |
| 回溯里只有 `push_back` 没有 `pop_back` | 状态污染，答案错乱 | 修改和恢复成对出现了吗？ |
| 保存了 `vector` 元素的引用/指针，之后又 `push_back` | 引用失效（UB） | 保存的是下标还是引用？ |
| 缓存里存 `iterator` / `T*` | 底层容器改动后失效 | 谁保证被指向的元素还在？ |

## 十分钟 code review 流程

不要从头读到尾。按下面四步，每步只问一类问题。

**第 1–3 分钟：函数边界。** 只看签名和头几行。参数是借用还是拥有？返回的是值、引用，还是指针？有没有输出参数在偷偷返回借用？这一步能拦下大部分"接口层面就错了"的设计。

**第 3–6 分钟：数据流。** 跟着一个对象走完它的一生：在哪创建、被谁传走、在哪里修改、在哪里销毁。重点看三处：容器扩容、`erase`、对象的 `reset`/析构。凡是"保存了句柄"和"修改了容器"出现在同一个函数里，就逐行确认顺序。

**第 6–8 分钟：回调与线程。** 搜 `detach`、`async`、`subscribe`、`post`、`capture`。每找到一个，问两个问题：它什么时候执行？执行时它捕获的东西还在吗？再看锁：临界区是否覆盖了数据的完整使用，而不是只覆盖了取值。

**第 8–10 分钟：测试。** 打开 sanitizer 构建（ASan + UBSan，线程相关加 TSan），跑一遍相关测试。再想想：有没有哪个测试是"只跑一次就对、跑两次就错"的？那通常意味着状态没有被重置。最后补一个针对本次改动的失败用例——**能复现的 bug 才算修好**。

## 如果你只能记住五句话

1. **每个句柄都要回答"它指向的东西还活着吗"**——迭代器、指针、引用、`string_view`、`weak_ptr` 都算。
2. **连续存储的容器怕扩容，节点存储的容器只怕删除自己**；凡是"先存句柄、后改容器"的代码，都要逐行核对顺序。
3. **改动和恢复必须成对，并且作用域要对齐**——回溯、锁、注册回调，都是同一件事。
4. **`join` 是唯一能证明"线程活不过对象"的工具**；`detach` 之后，所有引用捕获都默认是错的，除非你能写出证明。
5. **"能跑"不是证据**：UB 的典型表现就是偶尔正确；要么用 sanitizer 验证，要么把代码改成不需要验证的形式。

<strong>如果只记住一件事：</strong>生命周期的所有问题，最终都收敛成一个问句——"我手里的这个东西，在我用它的时候，它还活着吗？"把它问出口，比记住一百条规则有用。

## 本章小结

- 清单按"边界 → 数据 → 容器 → 递归 → 并发"的顺序使用，先确定借用/拥有，再谈同步。
- 六组问题覆盖了存储期、所有权、视图、容器失效、回溯恢复、线程与回调；每组都能独立使用。
- 红色信号表用来做快速筛查，命中不一定是 bug，但必须能解释为什么不是。
- 十分钟流程的重点是顺序和取舍：先看接口，再看数据流，最后才看并发和测试。
- 能复现的 bug 才算修好；sanitizer 是验证 UB 的最低成本手段。

## 自查任务

1. 打开你最近写的一个函数（200 行以内），按上面六组问题逐条过一遍，把每个"这里不用考虑"的理由写下来。至少记录一个改进点，并说明它属于哪一组。
2. 在你的项目里搜一遍 `detach`、`[&]`、`string_view` 成员、`erase(`，每个命中都用红色信号表对照一次，记录真实存在的问题数量。
3. 给一个已有的类补一个 `weak_ptr` 版本的回调注册，并写一个测试：对象销毁后触发事件，确认不会崩溃。
4. 用 ASan + UBSan 跑一次测试套件，看看有没有被"能跑"掩盖的失效访问。
